# Self-hosted contact inbox — unreleased, owner review only

This independent Helm chart belongs only in the restricted `stadtstack-contact` namespace. Public HTTPS `stadtstack.eu/api/contact` (Exact) reaches the receipt API on8081; the site `/` ingress remains separate. A successful `{ok:true}` means the message was saved in the encrypted own inbox, not emailed, read or replied to. Form submission does not send email.

Build the contact image with `docker build -f contact-service/Dockerfile contact-service`. The contact image must be the reviewed immutable public GHCR digest from the successful push-triggered `.github/workflows/contact-image.yml` run. `ntfy.image.digest` pins the official v2.29.0 multi-architecture index `sha256:4c599cf0818965782f93f652bd843e92714992e84d6b88ad17713dc0951cda1f`; this pin is not owner release approval. Anonymous image availability and selected platform must be reviewed for both images.

Contact runs one replica with Recreate strategy (single persistent store and in-process abuse limits). Its own `stadtstack-contact-inbox` ReadWriteOnce PVC requests1Gi; `storage.storageClassName` deliberately has no implicit default and must be owner-approved. Maximum messages defaults1000 (encrypted files bounded32KiB each, about32MiB plus an atomic temporary file). Ciphertext is stored under `/data/inbox`, a child of the PVC mount that avoids volume-root `lost+found`, using AES-256-GCM and a stable32-byte encryption key; name is optional and reply email is required. Startup cleanup, scheduled cleanup every60seconds and expiry checks before access enforce the90-day boundary; expired data is never returned. The backend exposes no public read/list/delete routes. Resource sizes are initial bounds, not load-tested sizing.

Both workloads require UID/GID1000, fsGroup1000, RuntimeDefault seccomp, no service account token, all capabilities dropped, no privilege escalation and read-only rootfs. Only each workload's `/data` PVC is writable. ntfy has a separate1Gi RWO PVC for `/data/user.db` (users/ACLs/tokens) and `/data/cache.db` (generic notifications,12-hour cache); attachments are disabled. Owner-approved storage encryption/Secret RBAC is required for ntfy's authentication material; the application's AES-GCM message encryption is a separate boundary. PVCs have `helm.sh/resource-policy: keep`: Helm uninstall must not accidentally erase the inbox or auth state. Retained/stopped stores and backups require owner-managed deletion within approved retention, since automatic cleanup needs a running service. The inbox key must survive restarts/upgrades; rotation requires a reviewed decrypt-and-reencrypt migration. Key loss makes existing messages unreadable.

## Private admin and notifications

`stadtstack-contact-admin` is **ClusterIP8082 only**, separate from the public8081 Service. There is no admin Ingress, host route, NodePort, LoadBalancer or8082 pod-ingress allowance. Admin reads and deletes require the mandatory `CONTACT_ADMIN_TOKEN` bearer token. The private UI shell at `/` does not disclose messages without authentication; health endpoints are not private-access proof.

`stadtstack-contact-ntfy` remains a same-namespace ClusterIP8080 Service, but now has the owner-requested **authenticated public HTTPS endpoint `https://ntfy.stadtstack.eu`**. Its default ACL is `deny-all`. Identity `owner` has read-only access to topic `contact`; identity `contact` has publish-only access to that topic. Anonymous access and other topics are denied. Both are regular users, not ntfy administrators. Public signup is disabled. Contact publishes with mandatory Secret `NTFY_TOKEN` bearer authentication to `http://stadtstack-contact-ntfy:8080/contact`; the entire notification body is **`Neue Kontaktanfrage auf stadtstack.eu`**, without message, name, reply email, IP, inbox identifier or admin link. Notification failure is visible in private inbox metadata; successful storage does not promise notification delivery.

For iOS instant notifications, ntfy's approved `upstream-base-url: https://ntfy.sh` sends a **content-free pseudonymous poll trigger**, not the notification body: SHA-256 of the topic URL and `X-Poll-ID` identifying the event. ntfy.sh relays through Google Firebase and Apple APNs; the authenticated iOS app retrieves the generic notification from our own HTTPS endpoint. This is not anonymous: topic hash, event identifier, timing and source-network metadata may be visible to relay providers. Own Firebase/Web Push credentials and attachments remain disabled. No visitor PII or generic body is forwarded upstream. [Primary ntfy iOS design](https://docs.ntfy.sh/config/#ios-instant-notifications). Actual sleeping-device delivery depends on iOS permissions/network/provider behavior and remains an owner-observed live acceptance gate, not a local-test claim.

The namespace default-denies ingress/egress. The owner-approved production HAProxy/Flannel peer set reaches contact8081 and ntfy8080; exact contact pods also reach same-namespace ntfy8080. Contact egress is **only** kube-system/kube-dns TCP/UDP53 plus same-namespace ntfy8080. **Only ntfy** gets public IPv4 TCP443 using the existing Ledger pattern: exclude private, cluster, loopback, link-local, shared, multicast/reserved, all three public node addresses and both load-balancer addresses (including77.42.11.9). This is not FQDN enforcement: ntfy is configured for verified HTTPS ntfy.sh, but NetworkPolicy permits other public HTTPS destinations. Live enforcement remains an acceptance gate. HTTP01 solver8089 is bounded to exact HAProxy sources; no private-admin pod-ingress grant exists.
